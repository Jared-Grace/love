# Shared constants: merge freely, never revalue

*Moved out of `CLAUDE.md` when that file reached its size ceiling. It is needed exactly when you are merging two spellings of a value, writing a new getter, or touching a value that has already escaped to a user's disk — not on every session, which is why it lives here.*

**Two files spelling the same value get one function, and you don't stop to judge whether they mean the same thing by it.** That question can't be answered when you're looking at them — a coincidence and a convergence look identical until something forces them apart, and *the forcing is the answer*. Guessing months early is what produced the "route this one, leave that one" reasoning this section replaces, and re-derived it every time somebody read the report.

**What makes that safe is that a split costs nothing, provided you never change a shared value in place.** When one site needs something different:

1. Rename the shared function if a clearer name helps (optional).
2. **Write a second function holding the new value** — `function_new_getter <name> <meaning> <value>` does the whole thing in one command.
3. Move sites to it **one at a time**. Migrating case by case is the point, not a limitation: it asks "does *this* one mean the new thing?" at the only moment the answer exists.

The old function keeps its old value throughout, so nothing already written moves.

**The one exception: a value that has already left this repo.** A localStorage key, an IndexedDB key, a word in a bookmarked URL — the data is on disks you can't reach, so an in-place change makes every future read look for the new word while every past write keeps the old one, and no later split can go back and fix it. Those are named in `literals_frozen_names()`; `literals_frozen_gate_run` (in `q`) reads each one's value off its own source and refuses a change the record doesn't have. **A deliberate change is still allowed** — `literals_frozen_write` regenerates the record, and the changed file standing in the commit is the point. **Add a name to that list whenever you write a new key that escapes**; nothing detects that for you, and a check that guessed which values had escaped would be back to guessing meanings. Use `literals_frozen_record_new` to record a newly frozen name — it only ever *adds* a name the record is missing and cannot touch a value the record already holds, so it can't quietly bless a change; `literals_frozen_write` regenerates everything and is the one to reach for when a value is deliberately moving.

**`text_frozen("word")` is the sibling of `fn_name("word")`, and the two mean opposite things.** `fn_name` says *this word IS a reference* — `function_rename` follows it, which is exactly what you want for a name. `text_frozen` says *this word only looks like a name*: the auto pass leaves it alone (it's in `js_strings_add_reference_skip_nodes`), and `js_code_getter_literal` reads it, so the freeze list can watch it. Without it a frozen value that happens to match a function name is **silently promoted to a reference to that function** by `ao` — which both drags that function's imports in and makes a value already sitting in users' browsers start tracking a rename. Real case: `app_a_indexeddb_database_name()` is the IndexedDB database, named after `app_a` because that is where the word came from; written plainly, `ao` turned it into `app_a.name`, importing the app entry point (measured at 410 KiB on the g bundle) into a function every file read reaches. **A database is not renamed by renaming code**, so that name has to be free to stop matching the app the moment the app is renamed.
