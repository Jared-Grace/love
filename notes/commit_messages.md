# What a commit message may contain

**Nothing is stripped out of a commit message, and nothing needs to be.** `git_call_message` joins the name and its arguments and hands them over as-is. It used to route every message through a stripper that turned `"` and shell operators into spaces, which was right while the commit was built by pasting the message into a line of command text between two quote marks — a `"` ended the quoted run early and the rest arrived as further arguments to git. Git is spawned from a **list of words** now (`git_folder_run`), so the message arrives as one word whatever is in it, and the stripping only destroyed the arguments it was there to record: a rename of a parameter written with dollars logged as a command nobody could run again. So don't hand-escape at a call site and don't add a stripper back; if a message ever does come out wrong, the fault is a line being built somewhere, not a character being let through.

The wider shape: **a defence written for one medium becomes damage in the next.** The stripper was correct against a shell line and wrong against an argument list, and nothing about the stripper itself changed in between — only what it was handed to. When a sanitizer looks unnecessary, ask what it was defending against and whether that path still exists, rather than leaving it in because removing it feels risky.

What is *not* free is the content of the arguments. `love` is a public repo and the human does not read commit messages, so anything in one reaches the public unreviewed. The rule that the args must be a command's real arguments — never a hand-written description — is in `CLAUDE.md` under Conventions and is unaffected by any of this: the stripper never enforced it and could not have.
